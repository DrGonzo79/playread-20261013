# CEO review — PlayRead

**Mode:** scope reduction. The full vision combines secure build ingestion, static analysis, asset provenance, playtesting, production planning, commercial comps, benchmarks, and legal conclusions. That surface is irresponsible before one paid memo exists.

## Premise, alternatives, and direction

The business outcome is a defensible greenlight decision, not a clever technical score. The first product must expose evidence, uncertainty, and human judgment. A deterministic snapshot is reversible; accepting unreleased source code and issuing legal conclusions are high-magnitude trust decisions.

`CURRENT: fragmented scout/producer/lawyer notes → THIS PLAN: explainable fictional-data risk snapshot → 12-MONTH IDEAL: secure evidence room + outcome-calibrated benchmark corpus`

Alternatives: (A) concierge memo, S/medium risk, fastest revenue; (B) ephemeral scanner plus analyst, M/medium-high risk, recommended after secure-compute proof; (C) continuous portfolio platform, XL/high risk, ideal architecture only after 50+ memos. The demo implements a thin representation of A’s decision format, not C’s ingestion system.

## Eleven-section review

1. **Architecture:** shared fixtures feed deterministic assessment contracts in TypeScript and Python. Keep scanners, storage, and legal review outside the core. Nil, empty, invalid, and calculation errors are explicit.
2. **Error/rescue map:** missing candidate → `404`; invalid bounded metrics → `422`; no evidence dimensions → blocked assessment; simulated request failure → visible retry panel; stale selection → result is cleared. No silent defaults in the API.
3. **Security:** demo fixtures are fictional. Production launch gates include ephemeral isolated workers, malware scanning, encrypted transfer/storage, tenant isolation, NDA/retention controls, access logs, and deletion receipts. Never train on customer code by default.
4. **Data/interaction:** select candidate → inspect evidence → run assessment → receive verdict and risk drivers. Empty, loading, success, and error states are distinct. Filters never alter the underlying score; reruns replace stale results.
5. **Code quality:** stable evidence keys and one pure risk engine per runtime. Cross-runtime duplication is acceptable for a static frontend demo; fixture parity and contract tests limit drift.
6. **Tests:** Python covers sign/investigate/reject, boundary validation, and missing IDs. Playwright covers candidate switching, assessment, error recovery, focus filtering, keyboard-visible controls, and mobile overflow.
7. **Observability:** production needs assessment latency/failure rate, build ingestion/deletion receipts, risk overrides, false-positive/false-negative outcomes, time-to-greenlight, memo conversion, and security incidents with runbooks.
8. **Database/state:** the demo is client-only and disposable. Production needs immutable evidence artifacts, assessment versions, reviewer decisions, access events, and retention/deletion state; no database is justified here.
9. **API:** `POST /assess/{candidate_id}` returns versioned score, verdict, drivers, and evidence gaps. Bound payloads, authenticate tenant access, rate-limit scans, and separate technical indicators from legal conclusions.
10. **Performance:** browser scoring is tiny. At 100×, repository extraction, binary scanning, and playtest telemetry dominate; queue isolated jobs and cap file/CPU/time budgets.
11. **Design/UX:** verdict and confidence come first, then evidence drivers and gaps. Fictional/simulated labels remain visible. Loading, error, empty, focus, responsive cards, and contained horizontal overflow are required.

## Decisions

- **Accepted:** three fictional candidate fixtures, deterministic five-dimension assessment, evidence focus filters, visible uncertainty, simulated service failure/retry, FastAPI parity endpoint, and responsive static frontend.
- **Deferred:** real uploads, source-code scanning, asset fingerprinting, persistence, authentication, PDF signing, benchmarks, and live commercial data.
- **Not in scope:** legal advice, copyrightability determinations, malware-safe ingestion claims, autonomous rejection, or a deployed Python backend.
- **Kill criterion:** if fewer than two of ten qualified publishers share a build under NDA, or none pays at least $2,000 for a pilot, stop product development and sell only trusted consulting or abandon the idea.
